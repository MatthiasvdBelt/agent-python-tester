# Antigravity AI Agent Rules

## 1. Context & Architecture
* **Context Alignment**: When modifying, designing, or adding code/files in a Hub App, you MUST align all technical decisions (prioritizing Modularity and Speed) with both:
  1. `mattiest_core/docs/project_context.md` (for overarching shared core framework, security, and modularity principles).
  2. The root `project_context.md` of the current Hub App (for project-specific MVP scope and feature objectives).
  *Note: Project context alignment does not apply to styling.*
* **Modular Django**: Prioritize modular Django applications. Leverage established third-party packages (e.g., `django-allauth`, `django-crispy-forms`, `django-drf`) before writing custom logic.
* **The LEGO-Block Philosophy**: The ultimate goal of this ecosystem is to write highly modular, DRY code comprised of many small, highly decoupled, and interchangeable "lego-blocks" (submodule apps) that can be quickly combined and assembled into a brand-new project with minimal friction.
* **DRY Scripting Guard**: When writing Bash, Python, or standard script files, NEVER copy-paste execution blocks, payload constructions, or curl operations. Extract repetitive logic, layouts, and API requests into clean, reusable helper functions inside the script.
* **Interchangeable Modular Extraction**: If you identify functionality that could be reusable in other projects or is a logical candidate for a separate app, you MUST ask the user if it should be extracted. If yes, implement the `[/create-modular-app]` workflow from `mattiest_core` using the `"mattiest_*"` prefix (e.g., `mattiest_[name]`). If no, implement it directly inside the Hub App without extracting it.
* **License Compliance**: When adding any new `pip` package, verify it has an OSI-approved license (e.g., MIT, Apache 2.0) and append the package name and license type to `LICENSE-README.md` or the primary `README.md`.
* **Upstream Dependency Single Source of Truth**: When upgrading, patching, or resolving security vulnerabilities for packages inherited via `-r mattiest_core/requirements.txt` (such as `django`, `sqlparse`, `cryptography`), you MUST update the requirement directly in `mattiest_core/requirements.txt` (and its corresponding `version.py`) rather than introducing overriding or conflicting duplicate constraints in the Hub App's `requirements.txt`. The core submodule remains the single source of truth for all shared foundation dependencies.
* **Core Utility Promotion**: General-purpose helpers (e.g., date/time duration parsers, number formatting, math helpers, text transformation) that are independent of any single sub-app's domain logic MUST be implemented in or promoted to `mattiest_core.utils` instead of living inside local sub-app directories.
* **Single Point of Modification Invariant**: When adding, enhancing, or modifying cross-cutting capabilities, debug tooling, or system behaviors (e.g., local debug file inspectors, structured logging, security headers, token signing, mail dispatching, audit trails), ALWAYS implement the enhancement in its single canonical location (within `mattiest_core` or the domain's central base service). NEVER write ad-hoc logic or duplicate behaviors inside individual consumer apps, endpoints, or views. Always extend the central abstraction so that all sub-apps inherit the capability uniformly with zero custom glue code.
* **Language Policy**: Code, comments, docstrings, variable/class/function names, filenames, and all internal codebase files MUST be in English. However, user-facing text displayed on the website or application interface can differ from English if the main language of the Hub App is configured differently.
* **App-Specific GEMINI.md Guidelines**: When working on, modifying, or designing code within a specific Hub App directory (e.g. `[app]/`), always consult and adhere to `[app]/GEMINI.md` for app-specific domain rules, calculations, and UX patterns while strictly complying with `mattiest_core/GEMINI.md`. App-specific guidelines must be stored in `[app]/GEMINI.md` and NEVER in core documentation. When writing rules to an app-specific `GEMINI.md`, always abstractify principles so that specific values/naming are generalized and reusable for future use cases.
* **Modular Sub-App Backlog & Roadmap Isolation**: Whenever documenting future features, TODOs, ideas, or backlog items specific to a modular sub-app (e.g., `invoices`, `quote_engine`, `sfgame`, `mattiest_core`), ALWAYS record them in that specific sub-app's dedicated backlog file (`<app>/docs/backlog.md`). NEVER pollute the root project backlog (`docs/backlog.md`) with sub-app specific roadmap tasks. The root `docs/backlog.md` is strictly reserved for overarching repository, hub-level integration, or cross-cutting platform concerns.
* **Single Source of Truth for Product Emails**: In any standalone modular application or sub-product, the canonical contact and support email addresses MUST be defined as constants in the app's `constants.py` (e.g., `CONTACT_EMAIL = "info@..."`, `SUPPORT_EMAIL = CONTACT_EMAIL`). All views, services, management commands, context processors, and templates MUST import and reference these constants rather than hardcoding literal email strings. Do NOT use Docker or host environment variables for product branding emails.
* **Strict Domain Email Isolation for Stand-Alone Products**: When working within any modular application that represents its own independent product (e.g., `quote_engine` / OfferteGeregeld), you MUST NEVER use `<>@mattiest.com` emails in defaults, seed scripts, fallback accounts, templates, or notification handlers. Always use the product's dedicated domain email addresses.
* **Zero Hardcoded Emails in Templates**: NEVER hardcode literal email strings (e.g., `mailto:info@...` or plain-text email strings) in HTML files, partials, plain-text email bodies, or marketing templates. ALWAYS inject them dynamically via template variables (e.g., `{{ contact_email }}`, `{{ OG_CONTACT_EMAIL }}`, `{{ support_email }}`) derived directly from the application's canonical constants or context processors.
* **Humanized Sender Display Names on Email Dispatches**:
  - Whenever dispatching transactional, notification, or marketing emails across ANY hub app or modular sub-app via `send_mail_wrapper`, the `From:` sender header MUST NEVER be a bare anonymous email address (e.g. `info@offertegeregeld.nl` or `info@mattiest.com`).
  - Sender addresses MUST always be explicitly formatted with a humanized, contextual display name in standard RFC 2822 format:
    - Format: `"{Sender Name} <{email}>"` (e.g., `"Matthias van OfferteGeregeld <info@offertegeregeld.nl>"` or `"Matthias van MattieST <info@mattiest.com>"`).
    - In multi-tenant dispatches sent on behalf of client accounts, derive dynamic sender branding: `"{Tenant/Contact Name} van {Company Name} <{from_email}>"`.
  - Canonical constants (`DEFAULT_FROM_EMAIL`, `QUOTE_ENGINE_DEFAULT_FROM_EMAIL`, etc.) or centralized configuration resolvers must define or format the full RFC 2822 display name so all outgoing communications present a clear, personal, and professional sender identity automatically.
* **Zero Devaluing Phrasing & Premium B2B Positioning**: NEVER use cheapening, consumer-grade, or devaluing terms (e.g., *"kosteloos"*, *"gratis"*, *"gratis demo"*, *"gratis proberen"*, *"for free"*) across customer-facing copy, landing pages, forms, emails, or marketing collateral. Such phrasing undermines premium product authority and perception of enterprise reliability. ALWAYS use value-affirming, enterprise-grade terminology (e.g., *"vrijblijvende demonstratie"*, *"preview op maat"*, *"inbegrepen"*, *"inclusief persoonlijke inrichting"*).
* **Psychological Precision Metric Standard**: When presenting automated processing speed, turnaround metrics, performance statistics, or delivery times in customer-facing copy, marketing claims, and documentation:
  - ALWAYS use precise, measured benchmark values that optimize psychological trust, realism, and perceived system value (e.g. *"binnen 30 seconden"* for automated document generation / PDF delivery; *"binnen 1 werkdag"* for human onboarding).
  - NEVER use arbitrary vague spans (e.g. *"binnen 5 minuten"*, *"in een paar tellen"*). Keep benchmarks grounded in optimal cognitive credibility.
* **Strict Anti-Quick-Fix, Universal Pure DRY & Diagnostic Reversion**:
  - *Zero Duplicate / Ad-Hoc Mocks*: When any asset, component, layout, data structure, or functional requirement fails to render, compile, or execute properly across any context (e.g., web templates, emails, APIs, PDFs, or backend services), NEVER implement quick-and-dirty duplicate mocks, inline reproductions, synthetic hardcoded stubs, or ad-hoc workarounds. Always diagnose and resolve the root cause directly at the canonical single source of truth (e.g. configuration, data models, host routing, asset source, or pipeline resolvers) to keep the entire codebase 100% DRY.
* **Client Legacy Stack & Post-Purchase Scope Guard (Client Scoping & CSD Context Only)**: ONLY when conducting pre-sales client intakes, scoping client engagements, drafting Solution Designs (CSD), or creating Implementation Plans for external client projects (this does NOT apply to internal MattieST core infrastructure or isolated submodules):
  1. *Audit Existing Post-Purchase Tooling First*: Always identify existing operational software before proposing new middleware, inventory sync (e.g. Bol/Amazon/marketplaces), review engines, or ERP/WMS connectors. If post-order operations (fulfillment, review collection, marketplace stock sync) are already established (e.g., via Rylee, Picqer, Channable), explicitly exclude them from the greenfield MVP build and connect via existing webhooks/APIs rather than duplicating tools.
  2. *Phased Deferral Architecture for Secondary Pillars*: When a client elects to postpone a functional pillar (e.g., advanced CRM retention, loyalty flows, multi-language expansion), NEVER discard the work. Retain the complete architectural specification and technical blueprint, but cleanly isolate it into a dedicated, numbered follow-up phase (e.g., Phase 4), shift maintenance/scaling phases accordingly (to Phase 5), and adjust the initial implementation estimate and recurring monthly SaaS cost table to reflect the lean MVP launch.
  3. *Pre-Purchase vs Post-Purchase Scoping Separation*: In e-commerce migrations (e.g. WooCommerce to Shopify), maintain a strict boundary between Storefront & Pre-Purchase conversion (D2C storefront, native bundles, AI content machine) and Back-Office/Post-Purchase operations (handled by existing partner systems).

  1. *Functional Framing (WHAT, not HOW)*: Always describe what functional capability is delivered using enterprise-grade terminology (e.g., *"Centrale Content & Data Hub"*, *"Serverless AI Repurposing Engine"*, *"Social Media Distributie Gateway"*, *"D2C Lifecycle Marketing CRM"*, *"Geïntegreerde AI-Ontwikkelstraat met Beveiligingsvangrails"*, *"Shopify 2.0"*). This prevents the client from using the blueprint to self-implement.
  2. *Internal Confinement*: Concrete software names, integration recipes, webhook payload schemas, API keys, and workflow scenarios belong exclusively in confidential internal implementation plans (`INTERNAL_IMPLEMENTATION_PLAN.md`) and developer playbooks.
* **Client Design & Brand Asset Ownership (SOWs & Proposals)**: In client proposals, Solution Designs, and Statements of Work (SOW), explicitly state that the client is responsible for providing high-resolution brand assets, logos, copy, product media, and defining the visual styling/design preferences, while the developer delivers the underlying technical architecture, Liquid layouts, and functional components.
* **Pragmatic & Accessible Tone in Client Deliverables (Anti-Bureaucracy Invariant)**: In all client-facing reports, summaries, SOWs, proposals, and emails, NEVER use overly stiff, bureaucratic, or legalistic corporate phrasing (e.g., *"In opdracht van [Klant] is gerealiseerd..."*, *"op uitdrukkelijk verzoek van..."*, *"vormt de formele afsluiting van Mijlpaal X"*). * **Client-Facing Hour Redaction Invariant (CSD & Proposals Only)**: In customer-facing CSD documents, proposals, and fixed-price phase tables, NEVER disclose internal developer hours, hourly breakdowns, or hour estimates.
  1. *Value & Milestone Pricing Only*: Customer-facing budgets must present clear deliverables, calendar turnaround / lead time (doorlooptijd in weeks), and fixed/indicative milestone investments.
  2. *Internal Confinement*: Hourly estimations, task breakdowns, and developer margins are strictly reserved for internal playbooks (`INTERNAL_IMPLEMENTATION_PLAN.md`).
* **Client Tooling Brevity Guard**: When referencing tools or systems already owned and operated by the client (e.g., Rylee, Picqer, specific ERP/WMS), NEVER explain or lecture the client on what their own software does or is used for. State strictly WHAT our system will do with it (e.g., *"order-overdracht naar Rylee en Picqer"*).

## 2. Environment, Configuration & Commands
* **Docker Native**: Ensure all code is compatible with a Docker Compose environment. Use environment variables (via `.env` files) for all secrets and host-dependent strings.
* **Docker Service OOM Score Shielding**: In all production and infrastructure Docker Compose environments (`docker-compose.prod.yml`, `docker-compose.infra.yml`), critical persistent infrastructure services (specifically PostgreSQL database containers and primary Traefik reverse proxies) MUST explicitly define `oom_score_adj: -1000` to prevent the Linux Out-Of-Memory (OOM) killer from terminating data persistence engines or proxy routers during host memory spikes. Conversely, background AI runners, batch jobs, and ephemeral tooling containers must be configured with positive scores (e.g. `oom_score_adj: 500`) so the kernel sacrifices disposable workloads first.
* **Mandatory Docker Compose Environment Variable Synchronization**: Whenever introducing, modifying, or removing environment variables in `docker-compose.dev.yml` (or `config/settings.py`), you MUST ALWAYS immediately synchronize those environment variables across all other compose environments (`docker-compose.prod.yml`, `docker-compose.stage.yml`, and `docker-compose.base.yml` where applicable). In production/staging compose files, enforce required variable interpolation syntax (e.g. `${VAR_NAME:?VAR_NAME is required}` or `${VAR_NAME:-default}`) to prevent runtime container gaps.
* **Mandatory Domain, Subdomain & Traefik Router Synchronization**: Whenever introducing, modifying, or configuring any domain or subdomain across the application (e.g. in `config/hosts.py`, `HUB_DOMAIN_MAPPINGS`, or third-party redirectors such as `clicks.<domain>`), you MUST ALWAYS immediately and simultaneously update:
  1. `ALLOWED_HOSTS` in `docker-compose.prod.yml` (and all other active compose environments) to include all primary and sub-domains.
  2. The Traefik HTTP router rule (`traefik.http.routers.${STACK_NAME}_${COLOR}.rule`) in `docker-compose.prod.yml` with `Host(...)` matchers for each domain/subdomain so Traefik automatically provisions Let's Encrypt SSL/TLS certificates.
  3. Ensure corresponding local testing patterns exist in `config/hosts.py` (`.localhost` / `.nip.io`).
* **AWS Secrets Documentation**: Whenever a new environment variable or secret is added to `.env.example`, you MUST directly add/define it in the local `.env` file (creating `.env` if it does not exist), notify the user that this variable needs to be added to AWS Secrets Manager, and update the AWS Secrets Manager table in `mattiest_core/vps_initialization/README.md`.
* **Fail Loudly**: Configure the application to crash/fail loud at startup/runtime if critical configuration or environment variables are missing.
* **No Default Fallbacks & Universal Fail-Loud**: NEVER define fake default values, mock fallbacks, or placeholder strings (e.g., hardcoded company names, fallback entity fields, dummy emails, mock objects) in models, views, services, or templates that mask missing or invalid database/context state. When expected entity data, account context, or parameters are missing, the system MUST fail loudly and raise an explicit error (e.g. `ValueError`, `ObjectDoesNotExist`, `ImproperlyConfigured`) immediately rather than falling back silently.
* **No Default Values for Environment Variables**: Never use default values or fallbacks for any environment variables. Every environment variable used in settings, views, templates, template tags, or context processors must fail loudly if missing or improperly configured. You MUST NOT provide default fallback parameters (e.g., `config('KEY', default='...')` or `os.environ.get('KEY', '...')`). The configuration must always be correct and complete in the environment.
* **Strict Zero-Default Values for App Settings in settings.py**: In `config/settings.py`, NEVER provide fallback string defaults (e.g., `default='info@domain.nl'`) for modular sub-app settings (such as credentials, sender domains, default from emails, or database names), even when flags like `MAILING_ENABLED=False` or `DEBUG=True` are active. Use `default=None` and enforce explicit test settings via `@override_settings` in test suites.
* **Standardized dev.bat Workflow Execution**: In all workspaces containing `dev.bat`, ALWAYS use `dev.bat` as the exclusive entry point for development commands (e.g., `dev.bat test`, `dev.bat mm` / `dev.bat makemigrate`, `dev.bat up`, `dev.bat down`, `dev.bat scan`). NEVER run raw `manage.py` or direct host `pytest` commands that bypass `dev.bat` environment variable setups. If a resource-heavy or Docker command requires execution, output the exact `dev.bat` command and instruct the user to run it.
* **Mandatory dev.bat AWS Secret Comments**: In `dev.bat`, ALWAYS append an explicit comment behind every environment variable that MUST be stored in AWS Secrets Manager to be populated into the `.env` file on production (e.g. `:: MUST be in AWS Secret for production .env`).
* **Sub-App Auxiliary Variable Parity in dev.bat**: When introducing external service integration variables (such as Sentry/GlitchTip DSNs, CSP security report endpoints, or analytics website IDs) in `dev.bat`, ALWAYS define explicit entries for EVERY active sub-app alongside the primary Hub App. Append `:: MUST be in AWS Secret for production .env (<app description>)` annotations to every entry to prevent deployment omissions.
* **Mandatory CI/CD & Deployment Failure on Service Startup Failure**: CI/CD and deployment pipelines MUST ALWAYS fail and abort immediately whenever any container, sub-project service, or daemon (e.g. Traefik, PostgreSQL, Gotenberg, Umami, GlitchTip, Redis, Celery worker) fails to start, crashes, or fails health checks. Never allow silent background failures or partial deployments.
* **Auxiliary Services Deployment Priority & Web Startup Order**: In deployment pipelines and server initialization workflows, all auxiliary infrastructure and sidecar services (e.g., databases, Traefik, Gotenberg, GlitchTip, Umami, Tailscale, background workers) MUST be started and verified healthy in a pre-deployment phase (`pre_deploy.sh`) BEFORE initiating the blue/green deployment or traffic swap of the primary Hub App (`web`). The primary Hub App (`web`) MUST ALWAYS be deployed and started LAST. Any failure during auxiliary stack startup or health checks MUST immediately terminate the CI/CD pipeline with a non-zero exit code and prevent web deployment.
* **Command Restraint**: **NEVER** run Docker or resource-heavy commands directly. Instead, output the commands and explicitly instruct the user to run them and report any errors.
* **Exclusive `dev.bat` Development Execution Guard**: In all workspaces containing `dev.bat`, ALWAYS use `dev.bat` as the exclusive entry point for running commands, tests, migrations, and script executions (e.g. `.\dev.bat test ...`, `.\dev.bat mm`, `.\dev.bat up`). NEVER execute raw host Python commands (`python -c ...`), direct `manage.py` invocations, or direct host test runners that bypass `dev.bat` environment variable setups. If a resource-heavy or Docker command requires execution, output the exact `.\dev.bat ...` command for the user.
* **Container-Only Testing**: The AI agent runs on the host system, but the actual application and dependencies run inside a Docker container (managed via `dev.bat`). Never run python tests directly on the host machine. The AI agent MUST NOT run the tests itself, nor run `dev.bat test` on its own. Instead, the agent should output a single copy-pasteable command for the user to run tests for all changed modules together using file paths instead of Python module import paths (e.g., `.\dev.bat test mattiest_core/tests/test_settings.py budgetplanner/tests/test_views.py`), and instruct the user to run it.
* **Test Execution On-Demand Only**: DO NOT automatically run tests (`dev.bat test`, `pytest`, etc.) after routine code, template, styling, or functional changes unless the user explicitly requests running tests or asks to verify/validate test coverage in their prompt. Complete the requested file modifications directly without unprompted test executions.
* **PowerShell Statement Chaining Guard**: In Windows PowerShell environments, NEVER use `&&` to chain commands or statements. In PowerShell 5.1, `&&` is not a valid statement separator and triggers a terminating `ParserError`. ALWAYS use semicolon (`;`) to sequence commands on a single line, or execute each command as a separate isolated step.
* **Urllib Bandit Nosec**: When using `urllib.request` (such as `Request` or `urlopen`) in scripts or Lambda functions, always append the `# nosec B310` comment to suppress bandit security linter audit flags.
* **AWS Lambda In-Memory Token Caching**: When developing AWS Lambda functions or polling services that acquire external OAuth/API tokens, ALWAYS cache tokens in module-level global variables across warm container executions to avoid making redundant authentication API requests on every invocation.
* **Minimal Base Compose File**: Keep `docker-compose.base.yml` strictly minimal and generic. App-specific or optional service configuration environment variables (e.g., `SFGAME_DB_NAME`) must NOT be defined in the base compose file. Instead, define them only in the specific compose configurations where they are required (e.g., `docker-compose.prod.yml` or `docker-compose.infra.yml`). In Python/Django settings, always provide a default fallback in `config()` (e.g., `config('SFGAME_DB_NAME', default='...')`) to prevent validation/interpolation crashes in environments where the optional variable is omitted (e.g., local development or CI/CD runner).
* **Sub-Compose Environment Binding**: When executing `docker compose` commands targeting compose files in subdirectories (e.g. `projects/<sub-app>/docker-compose.yml`) from scripts or post-deployment hooks (`post_deploy.sh`), you MUST explicitly specify `--env-file` pointing to the project root `.env` (e.g., `docker compose --env-file /apps/${HUB_APP_NAME}/.env -f ... up -d` or `docker compose --env-file .env -f ... up -d`). This ensures sub-services reliably inherit secrets and configuration injected by the deployment pipeline.
* **Conditional Debug-Only Route Registration**: In all `urls.py` files across the hub app and modular submodules, any debug-only helper routes, test preview endpoints, or development reset handlers MUST NEVER be declared inside the unconditional `urlpatterns = [...]` list. Always conditionally append them at the bottom using `if settings.DEBUG: urlpatterns += [...]` to ensure zero production routing surface.

## 7. Django & DRF Expert Best Practices
* **Models & ORM**: Define schema in models; use Django migrations (`makemigrations`, `migrate`). Optimize queries using `select_related` (Foreign Key) and `prefetch_related` (Many-to-Many) to avoid N+1 query problems. Keep business logic in custom managers and querysets.
* **Views & URLs**: Utilize Class-Based Views (CBVs) for standard patterns and Function-Based Views (FBVs) for simple logic. Use mixins for reusable CBV logic. Assign name arguments to all URL patterns for reverse lookup.
* **Django REST Framework (DRF)**: Use Serializers for data validation/conversion and ViewSets/Routers for standard API routes. Implement robust permissions, authentication, and throttling.
* **Forms & Admin**: Leverage ModelForms for database-bound forms. Perform custom data validation in clean() methods. Customize the Django Admin using ModelAdmin and inline formsets.
* **Security**: Enforce CSRF protection, Django's built-in authentication, and input sanitization. In production, configure `SECURE_SSL_REDIRECT = True` and use environment variables for secrets.
* **Throttling & Rate Limiting**: When creating new views, determine if a throttle is required based on complexity (e.g. data processing intensive, database heavy, or email sending operations) vs. simple read-only views. Decorate views with `@ratelimit` or configure them accordingly using values from the central `ThrottlingRate` Enum registry. If needed, define new enum values using abstract naming conventions (e.g., categorizing actions by sensitivity or impact level rather than specific view names) to ensure reusability across modules.
* **Caching & Performance**: When creating or modifying cache-able components (e.g. templates, HTML partials, complex database queries, or context processor data), you MUST implement caching right off the bat as a standard best practice to optimize resource utilization and response times. Ensure that cache keys are unique, include appropriate invalidation signals/methods (e.g. invalidating on model save/delete), and bypass caching when `settings.DEBUG = True` to prevent stale cache issues during development.
* **Multi-Database Test Suite Declaration Invariant**: In any test suite interacting with models routed to isolated or non-default database aliases (via `MultiDomainDatabaseRouter` or app-level database routing), every `TestCase` class MUST explicitly declare `databases = {'default', '<app_db_alias>'}` (e.g. `databases = {'default', 'quote_engine'}`). For pytest test functions, decorate with `@pytest.mark.django_db(databases=['default', '<app_db_alias>'])`. Omitting `databases` causes Django test runners to block access to secondary databases, triggering `DatabaseQueriesNotAllowed` / `ConnectionDoesNotExist` errors during CI/CD execution.
* **CI/CD Error Remediation Workflow Invocation**: Whenever the user instructs the agent to fix or diagnose a CI/CD error/failure, the agent MUST immediately invoke and follow the `/fix-ci-cd-errors` workflow (`mattiest_core/.agents/workflows/fix-ci-cd-errors.md`).
